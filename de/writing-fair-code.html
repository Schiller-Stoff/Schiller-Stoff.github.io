Ausgewählte Texte · Forschungsdatenmanagement

FAIR ist eine Prüfung, kein Abzeichen.

Generierter Code ist Forschungsdaten. Der FORGE-Beitrag von 2025 liest ihn gegen alle vier FAIR-Prinzipien und findet bei jedem dieselbe Antwort: Das Werkzeug entscheidet nicht, die Prüfung entscheidet.

01

Warum es den Text gibt

Vibe-Coding senkte die Schwelle und erhöhte die Menge.

Wenn ein Modell die technische Schicht schreibt, können Menschen ohne Programmierpraxis funktionierende Software erzeugen. Das ist ein echter Gewinn. Es bedeutet aber auch, dass mehr Code ohne Vorgeschichte, Lizenz oder Test in Forschungsprojekte gelangt.

Der Beitrag, gemeinsam mit Leona Elisabeth Münzer für FORGE 2025 verfasst, stellt eine enge Frage: Kann dieser Code FAIR sein? Nicht, ob er nützlich ist, nicht, ob er originell ist – sondern ob er als Forschungsdaten auffindbar, zugänglich, wiederverwendbar und interoperabel sein kann.

Der Rahmen ist wichtig. Code in einem Repository ist kein Nebenprodukt der Forschung. Er ist der Beleg für eine Aussage.

02

Das Argument

Vier Buchstaben, vier Fehlerarten.

  1. 01

    Findable

    Mehr Code bedeutet mehr Metadaten und mehr persistente Identifikatoren, nicht weniger.

  2. 02

    Accessible

    Die Lizenzierung ist ungeklärt; Trainingsdaten sind undurchsichtig, und generierter Code kann geschützte Arbeit duplizieren.

  3. 03

    Reusable

    Die Qualität sinkt ohne Prüfung: Code-Smells, doppelte Blöcke, ignorierte Konventionen.

  4. 04

    Interoperable

    Halluzinierte Pakete, vergiftete Abhängigkeiten, Prompt Injection, private API-Schlüssel.

Findable ist ein Mengenproblem. Ein Produktivitätsgewinn, wie GitHub ihn 2023 berichtete, erzeugt mehr Quellcode, als ein Team beschreiben kann. Unbeschriebener Code ist kein auffindbarer Code.

Accessible ist ein Rechtsproblem. Es ist ungeklärt, wie weit generierte Inhalte unter das Urheberrecht fallen, die Trainingsdaten vieler Modelle sind unbekannt, und generierter Code enthält oft Fragmente fremder Arbeit. Über Material mit unklarer Herkunft lässt sich keine Lizenz mit gutem Gewissen erteilen.

Reusable ist ein Vertrauensproblem. Assistenzsysteme sind schlecht darin, redundanten Code zu entfernen, und uneinheitlich bei Konventionen. Eine Codebasis, die schneller wächst als sie aufgeräumt wird, verliert die Qualität, die Wiederverwendung vernünftig macht.

Interoperable ist ein Lieferkettenproblem. Ein Modell kann ein Paket nennen, das nicht existiert, oder eines, das existiert und nicht installiert werden sollte. Private Schlüssel und lokale Pfade machen Code weder wiederverwendbar noch interoperabel.

Die Schlussfolgerung lautet nicht, dass generierter Code schlecht ist. Sie lautet, dass FAIR eine Eigenschaft eines kuratierten Objekts ist. Die Prüfung ist die menschliche Nacharbeit, mit verbindlichen Regeln für Qualität und Lizenzierung.

03

Was 2026 trägt

Die Werkzeuge verbesserten sich; die Prüfung bewegte sich nicht.

Assistenzsysteme refaktorieren und dokumentieren heute besser als 2025. Die Benchmarks verbesserten sich. Die Zuordnung nicht: Ein Diff kommt weiterhin ohne verlässliche Auskunft darüber an, woher seine Teile stammen.

Das Lieferkettenrisiko wuchs, nicht schwand, als Agenten begannen, ihre Abhängigkeiten selbst zu installieren.

Was ich ergänzen würde: Provenienz als fünfte Anforderung. Welches Modell, welcher Prompt, welches Datum, welche Quellen. Ohne sie sind die anderen vier Behauptungen.

Was ich behalten würde: den Satz, dass eine Person den Commit unterschreibt. Er ist der einzige Teil des Arguments, der sich nicht automatisieren lässt.
